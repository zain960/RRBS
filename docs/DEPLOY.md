# Deployment

Three supported topologies. **Option A** is what `render.yaml` in the repo root
automates and what most of this document walks through; option B is documented
because the code already supports it; **option C** exists because Render now
requires credit-card verification before it will create even free resources, and
Vercel + Neon is the equivalent that does not.

| | Option A — single service | Option B — split |
|---|---|---|
| Frontend | Served by Express from `backend/public` | Hosted separately (Vercel / Netlify) |
| Origins | One | Two |
| `CORS_ORIGIN` | Unset — nothing is cross-origin | Required: the frontend's exact origin |
| `VITE_API_BASE_URL` | Blank — the bundle calls `/api` relatively | Absolute, e.g. `https://api.example.com/api` |
| Cost | One free web service + one free database | Two services |

Option A is the default because it removes the entire class of CORS and
API-base-URL misconfiguration: the browser only ever talks to one origin.

---

## Option A on Render

### What the blueprint creates

`render.yaml` declares two resources:

- **`rrbs`** — a Node web service running `npm start --prefix backend`, which
  serves `/api/*` and falls back to the React bundle for every other path.
- **`rrbs-db`** — a managed PostgreSQL instance. Its internal connection string
  is wired into the service as `DATABASE_URL`; the value never appears in the
  repo.

Both are on the free plan in the `singapore` region. Change `region:` on **both
resources together** — a free database is not reachable from a service in
another region.

### Steps

1. Push this repo to GitHub (`main`).
2. Render Dashboard → **New** → **Blueprint** → select the repository. Render
   reads `render.yaml` and shows the two resources it will create.
3. Render prompts for the two values marked `sync: false`:

   | Variable | What to enter |
   |---|---|
   | `SUPER_ADMIN_EMAIL` | The address you will sign in with |
   | `SUPER_ADMIN_PASSWORD` | A password you choose now — see the warning below |

4. **Apply**. The first build takes roughly 3–5 minutes.
5. Open `https://<service>.onrender.com` and sign in with the credentials from
   step 3.

### Verifying

| Check | Expected |
|---|---|
| `GET /api/health` | `200`, `{"data":{"status":"ok"},...}` |
| `GET /api/health/db` | `200` — a `503` means the database is unreachable |
| `/` in a browser | The React app, and a deep link like `/login` survives a hard refresh |

### What the build does

`scripts/render-build.sh`, in order: install dependencies (with
`--include=dev`, because Render sets `NODE_ENV=production` and both build tools
— `vite` and `prisma` — are devDependencies), generate the Prisma client, build
the frontend into `backend/public`, apply migrations, seed reference data.

Migrations and the seed run on **every** deploy. Both are safe to repeat:
`prisma migrate deploy` applies only what is pending, and the seed upserts on
unique keys — it never resets an admin password or tax rates already configured
through the app.

## Things worth knowing before you rely on this

- **The free database is deleted after 30 days.** Render does not extend it and
  the data is not recoverable. Upgrade the database to a paid plan, or take
  regular `pg_dump` backups, before this holds anything real.
- **The free web service sleeps after ~15 minutes idle.** The next request wakes
  it and takes 30–60 seconds. This affects the first visitor, not the data.
- **Set a real `SUPER_ADMIN_PASSWORD`.** The seed's fallback is the development
  password published in the README, which on a public URL is a known credential.
  The seed warns in the logs if it ever falls back. It also updates the admin's
  profile but never the password hash, so changing the variable later has no
  effect — change the password from inside the app.
- **Email is off by default.** `NOTIFICATION_CHANNELS=log` means notifications
  are recorded in the `notifications` table and written to the service log, but
  nothing is sent. To enable it, add `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` /
  `SMTP_USER` / `SMTP_PASS` / `SMTP_FROM` in the dashboard and set
  `NOTIFICATION_CHANNELS=log,email`. A blank `SMTP_HOST` keeps the transport
  skipped rather than failing a check-in.
- **`JWT_SECRET` is generated by Render**, not stored here. Rotating it in the
  dashboard invalidates every issued token and signs all users out.
- **Custom domain:** add it under the service's Settings. Nothing in the app
  needs to change — the frontend uses relative URLs, so it follows the domain.

## Option B — split deployment

Only the configuration differs; no code changes are needed.

**Backend** (Render / Railway / Fly): deploy `backend/` as above, but set
`CORS_ORIGIN` to the frontend's exact origin — scheme included, no trailing
slash, comma-separated for more than one. Do not use `*`: the API is called with
a bearer token, so allowing any origin to read responses is a real exposure.

**Frontend** (Vercel / Netlify): build command `npm run build --prefix
frontend`, output directory `frontend/dist`. Set `VITE_API_BASE_URL` to the
API's origin including the `/api` suffix. Vite inlines `VITE_*` at build time,
so changing it means rebuilding, not restarting.

The host must rewrite unknown paths to `index.html`, or deep links 404 on
refresh — Vercel does this for SPA frameworks automatically; Netlify needs a
`_redirects` entry (`/* /index.html 200`).

## Option C — Vercel + Neon (no credit card)

Same single-origin idea as option A, but the API runs as a serverless function
instead of a long-lived process, and the database is hosted separately. Both
platforms have a permanent free tier that needs no card.

| Piece | Where | Config |
|---|---|---|
| Frontend | Vercel static output | `frontend/dist`, built by `vercel.json`'s build command |
| API | Vercel function | `api/[[...slug]].js` — exports the Express app unchanged |
| Database | Neon | Connection string goes in `DATABASE_URL` |

`vercel.json` drives it: it installs both workspaces, generates the Prisma
client, builds the frontend, and rewrites every non-`/api` path to `index.html`
so deep links survive a refresh.

`api/[...slug].js` is a **catch-all** rather than an `index.js` plus a rewrite,
because a rewrite would replace the request path and the router is mounted at
`/api`. As a catch-all, `req.url` still reads `/api/health` when it reaches
Express, so no route has to move. Express apps are already `(req, res)`
handlers, and `server.js` calls `listen()` only as a main module, so exporting
it is the whole adapter.

Use `[...slug]`, not the optional `[[...slug]]`. With the optional form Vercel
matched a single segment only: `/api/health` resolved, while `/api/health/db`
and `/api/auth/login` returned Vercel's own 404 without reaching Express.

### Steps

1. **Neon** → new project. Pick the region closest to the Vercel one (default
   `iad1` / AWS `us-east-1`) — every query pays that round trip.
2. Apply the schema from a machine with the repo checked out, since Vercel's
   build has no reason to touch the database:
   ```sh
   export DATABASE_URL="<neon pooled connection string>"
   export SUPER_ADMIN_EMAIL="you@example.com" SUPER_ADMIN_PASSWORD="<chosen>"
   npm run db:deploy --prefix backend && npm run db:seed --prefix backend
   ```
3. **Vercel** → Add New → Project → import the repo. It reads `vercel.json`;
   leave the framework preset as **Other**.
4. Set environment variables: `DATABASE_URL`, `JWT_SECRET`
   (`openssl rand -base64 32`), `NODE_ENV=production`, `TRUST_PROXY=1`. The
   `SUPER_ADMIN_*` pair is not needed here — the seed already ran in step 2.
5. Deploy, then check `/api/health`, `/api/health/db` and a deep link.

### Where this option is weaker than A

- **Vercel's Hobby plan is for non-commercial use.** Running a real property's
  bookings on it is outside their terms; that use needs Pro, or option A.
- **4 CPU-hours of active compute per month**, and 1M invocations. Fine for a
  demo, not a busy back office.
- **Cold starts on both tiers.** The function spins up per request after idle,
  and Neon's compute scales to zero after 5 minutes.
- **Neon free is 0.5 GB** and suspends compute if the monthly limit is hit.
- The API is serverless, so anything assuming a persistent process — in-memory
  caches, background timers — would not survive here. The app has none today.

## Deploying anywhere else

Nothing in the app is Render-specific — it reads plain environment variables
(`backend/.env.production.example` documents every one). On a VPS the sequence
is the same as `scripts/render-build.sh`, then run `npm start --prefix backend`
under a process manager with Nginx in front. Set `TRUST_PROXY` to the number of
proxies ahead of the app (`1` for Nginx alone, `2` with a CDN such as Cloudflare
in front of it) — rate limiting keys on the client IP, and trusting more hops
than exist lets a caller spoof `X-Forwarded-For` past the throttle.
